Thin deploy workflow

Add .github/workflows/deploy.yml in the Bedrock repo. Same pattern as the Laravel app: secrets stay in the app repo; deploy logic lives in platform.

name: Deploy to production

on:
  push:
    branches: [master]
  workflow_dispatch:

jobs:
  deploy:
    uses: Wiltzsu/platform/.github/workflows/reusable-deploy-bedrock.yml@master
    with:
      deploy_path: /var/www/site
      theme_path: web/app/themes/mydevsite
      php_version: "8.4"
      node_version: "20"
    secrets:
      SSH_KEY: ${{ secrets.SSH_KEY }}
      HOST: ${{ secrets.HOST }}
      USER: ${{ secrets.USER }}

deploy_path must match bedrock_deploy_path from Part 3. The workflow builds theme assets in CI, uploads Bedrock paths over SSH (excluding .env, vendor, and uploads), then runs composer install --no-dev on the server.

First deploy

Commit deploy.yml and push to master (the workflow triggers on master, not development). Check the Actions tab — a green run means code is on the server at /var/www/site.

Then SSH in and install PHP dependencies (WordPress core and plugins come from Composer, not the tar upload):

cd /var/www/site
composer install --no-dev --optimize-autoloader

Production .env and salts

Ansible created .env with placeholder salts (generateme). Before go-live, replace all eight keys from roots.io/salts.html. Use a fresh set for production — do not copy local dev salts.

Confirm DB_NAME, DB_USER, and quoted DB_PASSWORD match production. If the password contains $, keep single quotes around the value in every .env on the server.

Move the database (local → server)

Export on the local machine where WordPress content lives — not on the server. The production database starts empty; mysqldump on the server would only export that empty shell.

Local wp CLI was broken on my machine, so I used mysqldump directly:

# local — DB name from Bedrock .env (e.g. mydevsite)
mysqldump -u root -p mydevsite > ~/site-export.sql

# copy to server
rsync -avz ~/site-export.sql server:~/

# server — import into Part 3 database (e.g. site)
mysql -u user -p site < ~/site-export.sql

Verify import:

mysql -u user -p site -e "SHOW TABLES;"
mysql -u user -p site -e "SELECT COUNT(*) AS posts FROM wp_posts;"
mysql -u user -p site -e "SELECT option_name, option_value FROM wp_options WHERE option_name IN ('siteurl','home');"

A post count matching local (e.g. hundreds of rows in wp_posts) confirms the import worked. If siteurl and home still show http://site.local, run search-replace next.

Uploads

# local, from Bedrock project root
rsync -avz web/app/uploads/ server:/var/www/site/web/app/uploads/

Deploy excludes uploads from the tar — media stays on the server across deploys and is synced separately for the initial migration.

Search-replace URLs

Install WP-CLI on the server once (not included in the deploy tar):

cd /var/www/site
curl -O https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar
chmod +x wp-cli.phar
sudo mv wp-cli.phar /usr/local/bin/wp

wp search-replace 'http://site.local' 'https://site.example.com' --all-tables --path=web/wp
wp search-replace 'https://site.local' 'https://site.example.com' --all-tables --path=web/wp
wp cache flush --path=web/wp

Bedrock keeps WordPress core under web/wp — pass --path=web/wp on every WP-CLI command. After search-replace, home should be https://site.example.com and siteurl should be https://site.example.com/wp (Bedrock’s usual layout).

DNS and SSL (go-live)

In Cloudflare (or your DNS provider), point the registered domain at the server — records go in that domain’s zone, not as nested names under another zone:

@ (site.example.com)    A       YOUR_SERVER_IP
www                      CNAME   site.example.com

Use DNS only (grey cloud in Cloudflare) on @ and www for the first certbot run if the HTTP-01 challenge fails. Re-enable the proxy after HTTPS works.

  1. Confirm curl -I http://site.example.com hits nginx (301 to HTTPS from WordPress is fine once URLs are updated).
  2. sudo certbot --nginx -d site.example.com -d www.site.example.com
  3. curl -I https://site.example.com — expect HTTP/2 200 without certificate errors.
  4. Smoke test: home page, blog archive, wp-admin login, one post with media.

Progress checklist

Gotchas

  • Push to master — the deploy workflow does not run on development unless you change on.push.branches.
  • mysqldump direction — export local, import server. Do not dump the empty production DB.
  • HOST is the server IP — origin server for SSH, not a CDN hostname.
  • SSH_KEY is the CI deploy key — not the key you use from your laptop.
  • Table prefix — if not wp_, adjust SQL and WP-CLI commands accordingly.
  • Registered domain vs Ansible typo — I configured the wrong spelling in Ansible once. DNS records for the typo inside the real zone became a fourth-level hostname, not a public site. Match bedrock_domain to the domain you own before certbot.
  • Deploy path vs nginx root — GitHub Actions can deploy to /var/www/wiltzsu while nginx serves /var/www/wiltsu/web via symlink; only the paths in config need to exist.
  • Bedrock WP-CLI — always --path=web/wp.
