Centralizing Laravel deploys with a reusable GitHub workflow

After hardening my Ubuntu VPS, the next step in my homelab platform work was deploy logic. Grappling Tracker already deployed through GitHub Actions on every push to master — build assets, tar files over SSH, run Composer and Artisan on the server. It worked, but every step lived inside the app repo. A second Laravel site would mean copy-pasting ninety lines of YAML.

I pulled the deploy pipeline into a separate platform repo and wired the app to call it with workflow_call. One place to fix deploy logic; thin workflows in each project.

Before: everything in the app repo

The old deploy.yml did the full job inline: checkout, Node and PHP setup, npm ci, composer install, npm run build, upload via SSH, then remote cache and migrations. Fine for one app. Not a platform.

After: platform repo + thin caller

The reusable workflow lives in platform at .github/workflows/reusable-deploy-laravel.yml. It accepts inputs for deploy path, PHP/Node versions, and whether to run migrations. Secrets (SSH_KEY, HOST, USER) stay in each app repo — the platform repo never stores them.

Grappling Tracker’s deploy file shrank to this:

name: Deploy to production

on:
  push:
    branches: [master]

jobs:
  deploy:
    uses: Wiltzsu/platform/.github/workflows/reusable-deploy-laravel.yml@master
    with:
      deploy_path: /var/www/grapplingtracker
      php_version: "8.4"
      node_version: "20"
      run_migrations: true
    secrets:
      SSH_KEY: ${{ secrets.SSH_KEY }}
      HOST: ${{ secrets.HOST }}
      USER: ${{ secrets.USER }}

Push to master still triggers production deploy. The app repo owns when to deploy; the platform repo owns how.

What goes where

Gotchas that bit me

  • Branch pin — uses: ...@master must match the default branch on platform. I use master, not main.
  • Private repo access — if platform is private, enable workflow access under Settings → Actions so grapplingtracker (and other apps) can call it.
  • YAML indentation — jobs: sits at the root next to on:, not nested under it. GitHub silently mis-parses that one.
  • Secrets stay in the app — reusable workflows receive secrets from the caller; you don’t duplicate them in platform.

Verifying it works

Merge the thin deploy.yml to master and check the Actions tab — the merge itself triggers the run. No extra code change required. You can also re-run the last job from the UI or push an empty commit if you want another test.
